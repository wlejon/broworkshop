HarfBuzz shaping bro.text.shape() — ligatures, kerning, spacing, the cache

Every string in bro goes through HarfBuzz and comes back as a ShapedRun: a glyph array plus a cluster map from source bytes to glyphs. The map is the whole public contract — glyph ids never leave bro::render — and it is what makes the difference between shaping and a per-character lookup measurable rather than merely visible. src/render/shaped_run.h puts it bluntly: with shaping, "prefix measurement is wrong by construction".

Font families found on this machine

There is no font-enumeration API in bro, so presence is inferred by measuring: a family that resolves to the same face as a deliberately nonexistent name was not found (or is itself the fallback face). Reported, never silently skipped.

Ligatures — n characters, one glyph

A cluster spanning more than one byte and producing exactly one glyph is a ligature by definition. The first family above is used (Calibri on Windows, Hoefler Text on macOS) because it forms f-ligatures at default settings — an assertion written against Arial would prove nothing.

Kerning — the width of a pair is not the sum of its parts

The cheapest possible proof that shaping ran: kerning is a property of the pair, so any implementation that measures characters independently and adds gets a delta of exactly zero.

Prefix measurement is wrong by construction

letter-spacing suppresses ligatures; word-spacing hits only spaces

letter-spacing inserts space between characters, and a ligature has fused several into one indivisible glyph — so non-zero letter-spacing must turn ligatures off. It is a shaping input (it changes which glyphs exist) and lives in the cache key; the spacing amount does not, because it only repositions already-shaped output.

Bidi — UAX #9 bro.text.bidi() / bidiReorder(), cross-checked against shape() and layout

Three things must agree for RTL text to be right: level resolution (bro.text.bidi), reordering (bro.text.bidiReorder, rule L2), and the shaper, which runs both internally and emits its cluster map already in visual order. Each is checked against the others, then all three against the live layout with Range.getBoundingClientRect().

Resolved embedding levels, per code point

The glyph on top, its level underneath. Levels come back one per code point; runs come back in UTF-8 bytes. Confusing the two passes on ASCII and fails on everything else.

Astral text and grapheme clusters

An emoji is 1 grapheme, 1 code point, 2 UTF-16 units and 4 UTF-8 bytes — all four numbers are the right answer to some question. The cluster map reconciles them: a caret may sit at a cluster's start or end and never inside it. bro steps by cluster, not grapheme (no UAX #29 data in this build — see shaped_run.h), so sequences the font does not fuse show up here as more than one stop.

Multi-word strings — kerning does not stop at a space

Line breaking splits text at word boundaries, so the widths must still carry their neighbours' context: measuring each word alone drops every kern pair that straddles a space. Layout's width is checked against the whole string shaped once, with the isolated-word sum shown alongside — the number it must not be.

Selection & Range UTF-16 offsets at the JS boundary, UTF-8 bytes underneath

Everything above only read text. anchorOffset and Range.startOffset are UTF-16 code units per spec, the engine stores UTF-8 bytes, and a caret may only sit on a cluster edge. A binding that forgot to convert passes every ASCII test ever written, so the fixture is full of astral characters, combining marks and reversed text.

Every offset pair round-trips

Exhaustive rather than sampled: every ordered pair of legal offsets, each checked for startOffset, endOffset, collapsed and toString() against the JS string slice. An off-by-one-byte conversion survives a spot check and cannot survive this.

Offsets inside a surrogate pair

The DOM permits them, because JS string indices do. The claim is not that they are rejected — it is that nothing downstream turns one into U+FFFD.

Editing contenteditable, driven through the real input path

An editor holds three coordinate systems in agreement at once — UTF-8 bytes, UTF-16 code units and clusters — and every bug worth finding here is a place where two of them were confused. The scenarios drive the headless injection surface (keyDown, textInput, mouseDown) rather than synthesised DOM events, because the engine's key handler, hit test, focus resolution and contenteditable mutation path are what is under test.

Arrow stepping lands where the shaper says it may

The caret's stops walking RIGHT must be the shaper's own cluster stops, must be symmetric with walking back LEFT, and must never land between the halves of a surrogate pair.
